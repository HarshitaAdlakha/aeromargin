What the research says about evals that experts can trust.

Three questions shaped AeroMargin. How should an expert eval be built so that judges can trust it? What already exists for aerospace? And which engineering rules does each task rest on, so that two independent stress or performance engineers reach the same answer? For each one we used the strongest sources we could find: the guidance the hackathon points to, highly cited peer-reviewed work, and 2025–26 preprints where the field is too new for journals.

1 · How to build an eval you can trust

Demystifying evals for AI agents
Anthropic engineering guidance · the hackathon's recommended reading
Vocabulary (task, trial, grader, transcript, outcome, harness), the case for code-based graders, pass@k against pass^k, and a roadmap from a handful of hand-checked tasks to a trusted suite.
TookThe repository mirrors that vocabulary: tasks/, graders/, run_eval.py (harness), transcripts/. We report pass^3 next to the pass rate, because a stress engineer has to be right every time.
SWE-bench Verified, Terminal-Bench 2.0 (Harbor) and τ-bench
Jimenez et al. 2024 / OpenAI 2024 · Terminal-Bench team 2025 · Yao et al. 2024
Each task ships with a reference solution that must pass its own tests. Humans remove tasks that experts cannot agree on. Graders check the end state, not the path. τ-bench introduced pass^k to measure consistency.
TookEvery task has solution.py. An oracle run pushes each reference through the same harness and grader (10/10 pass). The graders check only the final JSON, so any valid method passes.
The Coin Flip Judge? Reliability and Bias in LLM-as-a-Judge Evaluation · Reliability without Validity
Yagubyan, arXiv 2026 · Norman et al., arXiv 2026 (21 judges, ~541,000 judgments)
Repeated identical LLM-judge runs flip pairwise verdicts 13.6% of the time on average. Cross-judge agreement was only κ = 0.51. Judge rankings shift by up to 14 places across benchmarks.
TookNo LLM judge at all. Every task has a defensible number or label, so all ten graders are deterministic code, with tolerances set from the precision of the input data.
GSM-Symbolic: Understanding the Limitations of Mathematical Reasoning in LLMs
Mirzadeh et al. (Apple), 2024 · ~730 citations
Performance drops when only the numbers change, and falls by up to 65% when one irrelevant-but-plausible clause is added. The authors argue that models replicate reasoning steps seen in training rather than reasoning.
TookThis is the mechanism we test in engineering form. Each task contains one condition that reverses a textbook default (a taper running the other way, an unsymmetric section, a wind in true degrees). A model that replays the familiar steps gets a confident, wrong answer.
Large Language Model Reasoning Failures
Song et al., Transactions on Machine Learning Research, 2026
A taxonomy of fundamental failures, application-specific limitations and robustness issues (inconsistent performance across minor variations).
TookWe report spread across trials as well as accuracy. The failures we see are mostly the "robustness" kind: the same model gets the same task right on one trial and wrong on the next.

None of these targets the step practitioners actually worry about: choosing the governing method and the right sign before doing the arithmetic. AeroMargin does, in ten tasks, each built around one known trap.

4 · What we deliberately did not do

  • No chart reading. Lug and column allowables that normally come from charts are given as numbers, so a correct answer never depends on how a curve is digitised.
  • No contested regulations. Where a factor's applicability is debated (for example, fitting factors on particular parts), the task states it.
  • No trick questions. Every trap is a condition a practitioner meets in real work and is expected to catch.
  • No copied benchmark items. All ten tasks, data sets and reference solutions are original. Borrowed ideas (task format, pass^k, oracle runs) are credited above.
